# 方案生成：待确认条件的统一校验设计

日期：2026-10-13。状态：设计草案，等待用户评审；不是已批准的实施计划。

## 1. 目标与已确认问题

目标是允许在条件尚未明确时提出有边界的技术草稿，同时继续拒绝虚构企业能力、把未知
条件当成已确认事实、无依据精确承诺以及失效引用。提高成功率不等于放宽准入权限。

当前 V2 仅阶段目标、任务、风险措施使用核验动作识别；时间安排、成果、风险影响、
里程碑等仍使用旧条件词判定。旧判定发现任一关联维度非 known 且没有指定条件表达时
即拒绝，不能充分区分核验动作、结果断言、假设风险和未来工作成果。

最近商机 242 / 分析 297 的实际调用先后暴露对象列表限定语问题与跨字段问题。最终一次
64 条建议的首个正式拒绝在 timing，semantic verifier 调用数为 0，未保存方案。
后续只读探针不是全部建议的最终审核结论。不能声称这 64 条建议均有效，也不能由此
要求客户补全所有信息。现场结果见 docs/known-limitations.md。

尤其必须区分：核验完成、核验通过、条件满足。三者不等价；完成核验可能得到不满足的
结果。“在核验完成后开展建设”不能自动被理解或改写成“条件满足后才建设”。

## 2. 方案选择

| 选择 | 收益 | 限制 | 建议 |
| --- | --- | --- | --- |
| 继续补充词表 | 局部改动小 | 不同字段规则分裂，未覆盖表述不断出现 | 仅作已定位缺陷的临时修复 |
| 统一确定性策略，保留现有协议 | 按内容用途和前置关系一致检查，错误可分类 | 仍需限定表达解析、反例验证和真实调用验证 | 本轮推荐 |
| 引入全新动作/依赖输出协议 | 可进一步压缩自由文本歧义 | 改变生成合同与兼容面，不是简单修复 | 留作后续单独设计 |

本方案不新增模型输出字段或模型自报的安全意图标签，不自动给原文添加条件或修改关联。

## 3. 判定职责与权威边界

现有事实准入、需求快照、readiness、严格结构解析、引用白名单、precision、语义否决、
返回时来源复核及人工审核继续各司其职。新的统一策略只替换目标 V2 规划字段中的
待确认条件判定，不赋予事实、能力或审核权限。

新策略是纯函数：读取原始建议、可信 placement、原始需求关联与冻结分析；没有模型、
数据库写入或状态晋升。内部分类来自程序，不接受模型声明“我是核验动作”作为通行证。
placement 只限定可表达的用途，不使该位置的任意内容自动合法。

仅在目标字段确有非 known 的真实关联维度时启用此用途判定。全部关联维度已明确的建议
继续原有校验，不因这套限定表达机制无法识别其普通技术表述而新增拒绝；这也不免除
事实、引用、精度和语义审核。冲突的 readiness 阻断规则不被用途判定覆盖。

内部判定明确分为候选、明确拒绝、无法可靠识别。候选仍需所有后续校验；无法可靠识别
不隐式通过，也不交由另一个模型批准。它应报告为表达需要技术核对，而不是客户缺信息。

分类解析采用可组合的对象、子句、前置关系和用途规则；不是继续维护各字段独立的整句
特例。每个子句都要检查，不能让一句免责声明或父级目标保护另一句无依据结论。
该解析仍是有边界的表达识别，不保证理解任意自然语言。

## 4. 内容规则与字段范围

| 内容用途 | 示例 | 处理 |
| --- | --- | --- |
| 待执行核验 | 核验部署条件并评估服务器容量是否足够 | 可送后续审核，不声称容量足够 |
| 条件性安排 | 经核验确认环境满足部署条件后，再安排部署 | 可送审核；条件仍未确认 |
| 前提不充分的安排 | 核验完成后直接部署 | 若部署依赖核验结果，不能把完成等同满足；需修正表达 |
| 计划形成的核验成果 | 形成容量核验记录，记录是否满足及差距 | 可送审核，不声称报告已经存在或结果必定通过 |
| 假设风险 | 若容量不满足，试点部署可能受到影响 | 可送审核，不将假设转成客户已有事实 |
| 核验里程碑 | 完成核验并记录结果和后续处理意见 | 可送审核，不承诺条件一定满足 |
| 已确认结论或保证 | 现有容量已足够；保证按期上线 | 仍须真实依据，不能以核验前缀、位置或未来时态豁免 |

以上是规则示例，不是免审句库。引用真实性、关联准确性、技术合理性和 atomicity 均须
另外通过；单句包含多个独立技术判断时，仍可由 semantic verifier 否决。

首次目标范围为 V2 implementation-phase objective/tasks/deliverables/timing、risk
condition/impact/mitigation，以及 milestone outcome。使用一张显式
用途策略表，按 section/container_kind/field 的完整组合路由，不按 field 名字单独放行。
这是相对当前三处例外的范围扩展，必须经本设计评审后才能实现。

实施前源码核对修正：原草案列过 milestone trigger/criterion，但当前 Atomic/semantic
合同均只允许 milestone outcome/timing，枚举成员存在不等于该 placement 合法。本轮
仅纳入已合法且原设计已覆盖的 outcome，不开放 trigger/criterion；milestone timing
与 risk trigger 保留原行为。实施计划会明确记录此修正，等待用户一并确认。

架构、部署与集成、验收标准等其余位置不因本轮规划类候选识别获得例外；V1 保留旧路径。
未知用途、非法 placement、无关联上下文或非法引用继续失败。任何分类都不允许清空关联、
改挂到无关已知维度、去掉技术判断或删掉关键结构以换取通过。

混合已知背景与未知容量的维度保持原状态，不从局部文本中自动拆出“已确认”子事实。
客户预算、期望日期和使用人数不是供应商报价、交期、QPS 或 SLA 的授权。

## 5. 生成与校验的一致性

生成输入中的表达指导由同一用途策略派生，避免提示词与实际判定各维护一套边界。
指导要求计划先核验，并按结果处理；不得保证核验必然通过。风险和成果使用正确的
假设/未来用途，不写成已经完成的事实。保留原始需求和所有待确认信息。

guidance 是输入信息，不成为事实依据。模型不服从时正常拒绝：不自动修补 JSON、
替换引用、拆分文本、添加免责声明或删除失败条目。不增加生成预算、尝试次数、模型
调用或 provider fallback。既有一次结构重新生成的边界保持不变。

有信息缺口但方向清楚的方案仍按 ready_with_gaps 路径处理；已存在的商业不确定性规则
不变。业务方向不足、真实冲突或不合格企业依据仍由现有 readiness/admission 拦截。

## 6. 面向使用者的错误提示

失败提示区分职责，不将所有 grounding 拒绝包装为补充客户条件：

| 类别 | 提示与下一步 |
| --- | --- |
| readiness 判定需要客户澄清 | 明确指出对应已保存快照的缺口/冲突；销售确认真实信息后创建新快照 |
| 缺合格企业事实 | 补充资料并由有权限人员审批事实；不是模型生成来填空 |
| 生成内容的前置关系不充分 | 提示对应可信栏目与问题类别，售前/维护人员核对生成表述 |
| 无依据事实、精度或承诺 | 明确说明未保存，不建议无变化重复生成 |
| 表达无法可靠识别 | 技术核对，不断言客户条件不足，也不直接认定模型结论有效 |
| 模型服务或格式异常 | 单独提示配置/服务/输出问题，不伪装成业务信息缺失 |

优先通过稳定、可信的错误代码映射区分类别，保留现有 HTTP/JSON 兼容字段和安全兜底。
详细位置来自程序生成的 section/field 与序号，不采用模型任意 key 或文本。受控诊断
使用请求关联编号、类别和位置，不在普通日志或错误响应中输出客户原文、模型完整输出、
来源正文、密钥或异常 cause。不能把失败内容当成可提交售前审核的方案。

幂等重放保留同一失败，不追加模型调用；原需求、分析、历史方案和审核记录不覆盖。

## 7. 验证与启用条件

先固定可核验的表达规则与字段用途矩阵，再写红绿测试。至少覆盖：

- 两次实际对象列表原句与第二/第三对象限定语；状态 unknown/unclear/conflict 均不晋升。
- timing 的完成/通过/满足区别；无法把否定、核验失败或前置条件不成立解释成成功。
- 未来成果与已完成事实、风险假设与实际状态、里程碑核验完成与保证成功分别成对验证。
- 混合句、伪条件、未经支持的产品/协议、预算、期限、服务器容量、QPS/SLA 和精度反例。
- 引用/上下文拒绝、语义 INADMISSIBLE/COMPOUND、无效 verifier 响应和 provider 错误。
- 返回期间审批、索引或来源变化仍拒绝；历史、权限、自审、stale 和 V1 行为不变。
- API 分类及前端下一步不能误导销售把技术表达故障当作客户需要补充信息。

先进行不改变正式决策的影子比对，只记录安全差异。所有新增候选路径和负例边界经过
评审及完整回归后，才启用新 V2 策略。不能在评估期间用新策略偷偷放行旧策略拒绝的内容。

真实验收使用正式保存的需求、已批准资料与正常工作流，记录结构校验、确定性判定、
语义否决、来源复核及保存结果。受控调用次数与成本应在实施计划中预先确定；不承诺
一次调用或任意自由文本都成功，不持续重试直到偶然得到成功。未生成即如实报告未通过。

本轮设计未运行新模型调用、修改业务数据、重启服务或操作 PostgreSQL 实例。
