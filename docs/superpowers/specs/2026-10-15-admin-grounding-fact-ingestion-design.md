# Admin 真实文档与待审事实入口设计

日期：2026-10-15。状态：用户在本规格交付后回复“继续”，进入实施计划阶段；不是已实现功能。

## 1. 已确认的目标与范围

用户已同意开始修改，并选择第一版使用 Django `/admin/` 后台，而不是新增
Vue 知识库页面。目标是让有权限人员不依赖 `seed_demo`、benchmark 或手工 shell，
完成“真实上传资料 → 索引就绪 → 明确发起事实抽取 → 人工批准/拒绝”。

抽取只提出候选事实；批准不等于事实永久有效，也不等于方案通过技术审核。
原方案准入、引用、当前索引、过期判断、verifier veto-only、返回时来源复验均保留。
本规格确认不表示已授权在业务库应用新增表，具体实施计划仍需审阅。

这属于跨模块功能：需要管理入口、可持久化的抽取执行状态和并发防重。
先批准本规格，再编写实施计划；实施计划还需审阅并确定执行方式。

## 2. 当前源码依据

- `apps/knowledge/api/serializers.py`：已有上传验证、可信文件元数据派生和创建人注入。
- `apps/knowledge/services/indexing.py`：已有初次索引和重建索引；外部 embedding
  在短事务之外；成功重建使旧事实 stale。
- `apps/knowledge/services/grounding_facts.py`：已有受控主题、严格结构/逐字摘录校验；
  模型调用后重新核对文档、index-run 和 chunk 快照，原子保存 PROPOSED。
- `apps/knowledge/admin.py`：目前只注册事实审核，禁止手工增加/修改事实。

## 3. 方案取舍

1. **选择：Admin 文档操作 + 显式抽取 + 既有事实审批。**
   复用已有管理会话和双门权限；状态清晰，不使一次重建索引隐式触发付费抽取。
2. 暂不选择：每次上传/重建索引后自动抽取。它耦合两种失败与费用，仍需防重和状态记录。
3. 暂不选择：新增 Vue 文档/事实工作台及独立审批 API。体验可以更统一，但不是本批范围。

## 4. 后台页面与权限

新增“知识文档”列表和只读详情，提供专用上传表单、单文档重建索引确认页、
单文档事实抽取确认页，以及按来源文档过滤的现有事实审核列表链接。

这些 Admin 入口统一要求当前用户 active、staff 且业务 role=admin。
技术 superuser、Sales/Presales、无 staff 的业务 admin 都不能借此获得管理或审批权限。
每个服务端操作都检查权限，不能只隐藏按钮；POST 时重新检查，而不是相信确认页。
不自动修改任何账号标记。现有业务 API 的权限和响应结构不变。

操作使用 Admin 会话、CSRF 和 POST；GET 仅展示/确认，不调用 provider、不写数据。
不提供批量抽取，不开放原始文件地址、存储路径、任意事实编辑或删除。
文档已有来源和派生元数据只读；修订文件需要作为新文档上传，不覆盖历史源文件。

## 5. 上传和索引

表单只接受标题、文档类型、文件；复用现有 serializer/文件验证，不另写宽松上传逻辑。
当前支持 UTF-8 TXT、Markdown 和可提取文字的 PDF，沿用大小、页数和解析限制。
不新增 Word 导入、OCR 或任意文件直传；Word/PDF 方案导出与此无关。

上传确认明确说明会进行索引，可能调用已配置 embedding 服务。
服务端设置 created_by，校验并保存后复用 index_document。
已验证上传的初次索引失败时保留 FAILED 文档及安全错误，不把上传全部伪装成未发生。
初次索引失败的重试不扩展现有状态机：第一版提示检查原因并重新上传；
READY 文档的重建索引复用 reindex_document，失败时保留旧可用索引的既有语义。

专用 Admin 操作不得把外部调用放入默认 change-form 长事务中：采用专用视图/服务，
保存/认领/完成使用短事务，解析、embedding 和 LLM 调用在事务外。

## 6. 抽取操作与最小执行记录

仅 READY、当前 index-run 非空、没有正在重建索引的文档可发起。
确认页展示文档、当前索引版本和调用模型的费用提示。POST 携带该索引版本，
服务端锁定文档后再次比较；页面过期则拒绝，不偷偷换成新版本。

新增 `GroundingFactExtractionAttempt`（工作名称）作为审计与防重记录：

- 文档引用（PROTECT）、冻结的 index-run、发起人（PROTECT）；
- RUNNING / SUCCEEDED / FAILED / CANCELLED 四种明确状态；
- 唯一执行 token、开始/完成时间、安全错误码、候选条数；
- 不保存密钥、模型原文或重复的文档正文。

同一文档同一 index-run 最多一个 RUNNING 或 SUCCEEDED 记录，数据库条件唯一约束兜底；
FAILED/CANCELLED 历史不覆盖。开始/完成时间、状态和条数需有一致性约束。
文档行锁保护认领与完成；全局锁顺序为文档 → 执行记录，避免反向取锁。

重复提交处理：

- RUNNING：提示已有执行，不再调用模型；
- SUCCEEDED：返回已有完成状态/候选列表，包括成功但零条候选，不再次付费；
- FAILED：必须进入明确的“重新抽取”确认页后才能新建一次尝试，无自动应用层重试；
- 当前版本已有历史事实但无执行记录：展示“已有历史事实”，链接原记录；不为凑状态
  伪造执行历史，也不再次抽取。需要新抽取时先明确重建索引；
- 模型内部传输重试沿用已有 provider 配置，不增加新一层格式重试或循环重试。

调用原抽取逻辑时，后台路径携带执行 token 和冻结索引版本；服务在保存候选前，
重新核对当前索引、chunk 快照和执行所有权。候选创建与 SUCCEEDED 转换必须同一事务完成。
不能在候选已经单独提交后再补写成功记录，否则崩溃后重试会生成重复事实。
现有非后台调用及测试默认行为保留，不把本入口的防重承诺扩大到所有内部工具。

进程中断不能被误判为成功，也不能仅凭经过一段时间自动重新执行。
RUNNING 长期未结束显示“状态未确认”；有权限人员可在专用确认页显式取消这次尝试。
取消与完成竞争同一文档/执行锁；取消撤销 token 的写入资格。旧请求之后返回也不得写入
候选或覆盖状态。重新发起仍需另一次确认，并警告旧外部请求可能已计费、无法远程撤销。
不引入任务队列、后台线程、定时清理、自动 lease 接管或新服务。

## 7. 审批、重建索引与状态展示

抽取候选始终 PROPOSED，approved_by/approved_at 留空；模型不能指定批准字段。
沿用现有人工 approve/reject 服务及双门权限。批准不会把未确认/冲突内容自动转换成
正向能力；方案仍通过现有确定性事实、来源和引用准入。

重建索引成功时，旧事实沿现有规则 stale；抽取记录留作历史。
新 index-run 可重新抽取，但候选不得继承旧批准人、批准时间或批准状态。
抽取期间发生索引切换或开始重建，不接受旧结果；保留安全失败原因，不回写旧内容。

列表/详情区分：未索引、索引失败、索引就绪未抽取、抽取中、抽取失败/取消、
成功无候选、存在待审事实，以及各审核状态计数。
展示“已批准”同时注明：**不保证可用于每一份方案，仍须通过当前来源与准入校验**。
不把 READY、SUCCEEDED、APPROVED 三种状态混成“方案依据已通过”。

失败只显示白名单安全错误/下一步，不回显异常堆栈、模型输出、密钥或未经转义的文件名。
表格与来源摘录保持 Django 自动转义，不用 mark_safe 展示上传或模型内容。

## 8. 明确不包含

- 不修改生成提示词、RAG 问答引用逻辑、审核图节点动作、限流/CI/日志架构或连接池。
- 不调用 seed_demo 填充真实业务库、不合成企业事实、不自动审批/提交方案审核。
- 不改既有方案、分析快照、provenance、历史事实或演示数据。
- 不新增 Vue 页面，不更改原知识业务 API。
- 不安装依赖、不重建 GitNexus、不提交或清理用户已有 Git 改动。
- 不重启或调整 PostgreSQL 实例、端口、配置、PID、角色、模板或扩展。

## 9. 数据库与运行授权边界

实现阶段预计只新增知识域执行记录表和相应 Django migration，不做历史数据迁移。
先在现有测试环境验证，不在用户业务库应用 migration，也不自动重启项目。
业务库 schema 应用和真实 provider 验收在实施验证后另行明确确认；本规格批准不能
被解读为授权 PostgreSQL 实例维护、自动消费真实模型额度或处理未指定的真实文档。

## 10. 验收条件

所有新增行为先写失败测试，再最小实现；自动化只用 fake/deterministic providers。

1. 无后台权限/错误业务角色/技术 superuser 越权/无 CSRF/GET 修改均不能调用 provider 或写入。
2. 合法 TXT/MD/PDF 经真实 Admin 请求边界可上传并索引；非法、超限、加密/不可提取 PDF
   沿用既有拒绝规则；文件元数据及发起人不能伪造。
3. 普通 Admin 流程无需 demo 即可抽取 PROPOSED、显示来源和审核入口；人工批准后，
   使用既有准入服务验证可引用性；拒绝、未批准和过期仍不能变成可用正向证据。
4. 重复 POST、并发请求、SUCCEEDED 零候选和历史事实都不会悄悄重复调用/保存。
   PostgreSQL 条件唯一和锁竞争须有针对性测试，不能只以按钮 disabled 作为证明。
5. 非法输出/外部失败没有半份候选，不损坏 READY 索引；显式失败重试保留旧记录。
6. 上传/抽取的外部调用处于短事务之外；完成时权限、token、文档/索引/快照再次核对。
7. 取消与完成竞争、旧请求迟到返回、抽取与重建索引交错均不产生旧版本候选或假成功。
8. Admin 审批复用原边界，历史演示/benchmark/提取服务测试保持兼容；不放宽方案门禁。
9. 相关专项和全量后端回归串行运行；迁移一致性、系统检查、现有前端测试和构建验证。
   若必须触碰与本功能无关的失败或基础设施，停下报告，不顺手修复。
10. 独立只读评审完成后报告结果与未验证项；离线通过不宣称真实 provider 质量或生产就绪。

## 11. 规格自检

- 仅 Admin 入口和知识事实衔接，无跨入其它审查条目。
- 明确零候选、失败重试、历史事实、并发、取消和索引变化，不以按钮或内存锁充当防重。
- 抽取只提议；业务角色与后台标记仍独立；准入与返回时复验不变。
- 记录表是拟议新增 schema，不假定已获业务库应用授权。
- 本文件未提交 Git；保留当前 dirty 工作区及用户保护文件。
